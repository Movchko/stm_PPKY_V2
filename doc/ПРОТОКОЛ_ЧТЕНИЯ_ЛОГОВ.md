# Протокол чтения журнала событий ППКУ

**Версия протокола:** 2 (`LOG_STREAM_PROTO_VER` в `Core/Inc/log_stream.h`)  
**Режим:** только чтение. Команд удаления и изменения журнала нет.

Формат записи и коды событий: [`event_log_catalog.json`](event_log_catalog.json), [`ЛОГЕР_СОБЫТИЙ.md`](ЛОГЕР_СОБЫТИЙ.md).

Источник поведения — текущая прошивка `stm_PPKY_V2`: `Core/Src/log_stream.c`, `Core/Src/log_transport.c`, `Core/Src/can_bus.c`.

---

## 1. Канал

| Канал | В прошивке | Параметры |
|-------|------------|-----------|
| **USART2 (ESP32 / Wi‑Fi)** | приём запросов и передача ответов | 1 000 000 бод, 8N1, без аппаратного потока (`MX_USART2_UART_Init` в `Core/Src/main.c`) |
| UART4 / RS485 | не используется | `LOG_PORT_UART4` объявлен в `log_stream.h`; `LogTransport_OnUartRxByte` пустой, передачи на UART4 нет |
| CAN | не используется | номера `ServiceCmd` 164…167 в `backend.h` помечены как резерв, обработчика нет |

Запрос журнала — кадр BSU с `pkt_type = 16` на USART2. Его разбирает приёмник моста в `Core/Src/can_bus.c` и вызывает `LogTransport_OnUart2LogRequest`. Входящие кадры типов 17 и 18 на USART2 отбрасываются.

Ответы типов 17 и 18 уходят в тот же USART2 и стоят в одной очереди с CAN-кадрами типов 0 и 1. Кадр журнала передаётся, когда очередь CAN-моста пуста и передача USART2 не занята (`UartBridge_IsTxIdle`). Очередь журнала — 32 кадра; при переполнении выбрасывается самый старый.

Каждый принятый запрос журнала один раз за сессию связи пишет событие `HOST_LINK` (код 15, `additional[0] = 0`). Повторная запись разрешается после `Esp32_SetEnabled(0)`.

**Лимит кадра:** 256 байт целиком (`LOG_STREAM_FRAME_MAX`). Полезная нагрузка — не длиннее 246 байт (`LOG_UART_BODY_MAX`).

**Инварианты выгрузки:**

1. `pkt_num` потока идёт 0, 1, 2… без пропусков внутри одной сессии.
2. В кадре только целые элементы потока (38 байт). Запись между кадрами не режется.
3. ПО запрашивает диапазон. ППКУ режет его кадрами сама.

## 2. Кадр BSU

Little-endian, тот же заголовок, что у CAN-моста (`device_lib/include/backend.h`, сборка в `Core/Src/log_transport.c`).

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | Преамбула `0x55 0xAA` |
| 2 | 2 | `pkt_size` — длина всего кадра, включая преамбулу и контрольную сумму, не больше 256 |
| 4 | 2 | `pkt_type` |
| 6 | 2 | `seq` |
| 8 | `pkt_size − 10` | `payload` |
| `pkt_size − 2` | 2 | `checksum` — сумма uint16 по байтам `[0 .. pkt_size − 3]`, младший байт первым |

`pkt_size = 8 + payload_len + 2`.

### Типы

| `pkt_type` | Имя | Направление |
|------------|-----|-------------|
| 0 / 1 | CAN / CAN2 | мост, к журналу не относится |
| **16** | **LOG_REQ** | ПО → ППКУ |
| **17** | **LOG_RSP** | ППКУ → ПО, одиночный ответ |
| **18** | **LOG_DATA** | ППКУ → ПО, поток |

`seq` в `LOG_RSP` равен `seq` запроса. `seq` в `LOG_DATA` всегда 0.

Пустой запрос (`payload_len = 0`) остаётся без ответа.

## 3. Команды

Первый байт payload запроса — `opcode`.

| opcode | Имя | Назначение |
|--------|-----|------------|
| `0x01` | `PING` | проверка связи |
| `0x02` | `GET_INFO` | ёмкость, число записей и `write_head` обоих уровней |
| `0x10` | `START_DUMP` | начать выгрузку |
| `0x11` | `STOP_DUMP` | остановить выгрузку |
| `0x12` | `GET_DUMP_STATUS` | состояние сессии |

Неизвестный opcode: ответ 2 байта, `status = 2` (`BAD_PARAM`), второй байт — эхо opcode.

Короткий ответ об ошибке, если он описан ниже, — всегда 2 байта: `status`, `opcode`.

### Коды `status`

| Код | Имя | Когда ставится |
|-----|-----|----------------|
| 0 | OK | команда принята |
| 1 | NOT_INIT | журнал не инициализирован |
| 2 | BAD_PARAM | короткий `START_DUMP`, `tier > 2`, неизвестный opcode |
| 3 | OUT_OF_RANGE | `start_logical` больше числа записей выбранного диапазона |
| 4 | BUSY | выгрузка уже идёт |
| 5 | FORBIDDEN | объявлен в `log_stream.h`, в ответы не записывается |
| 6 | INTERNAL | не удалось прочитать сведения об уровне |

Одновременно существует одна сессия выгрузки на всё устройство.

---

## 4. `PING` (`0x01`)

Параметров нет. Инициализация журнала не проверяется.

Ответ `LOG_RSP`, 4 байта:

| Смещение | Поле |
|----------|------|
| 0 | `status` = 0 |
| 1 | `opcode` = `0x01` |
| 2 | `proto_ver` = 2 |
| 3 | `record_size` = 32 |

`record_size` — размер записи во Flash, не размер элемента потока.

---

## 5. `GET_INFO` (`0x02`)

Параметров нет.

Если журнал не инициализирован: 2 байта, `status = 1`, `opcode = 0x02`.

Иначе ответ 32 байта:

| Смещение | Поле |
|----------|------|
| 0 | `status` = 0 |
| 1 | `opcode` = `0x02` |
| 2 | `proto_ver` = 2 |
| 3 | `record_size` = 32 |
| 4..7 | `critical_capacity` u32 |
| 8..11 | `critical_count` u32 |
| 12..15 | `critical_write_head` u32 |
| 16..19 | `general_capacity` u32 |
| 20..23 | `general_count` u32 |
| 24..27 | `general_write_head` u32 |
| 28..31 | `catalog_crc32` u32 |

`count` — число слотов, которые войдут в выгрузку (`EventLogTier_t.total_records`). Это не число записей с верной контрольной суммой: внутри диапазона `rec_status` бывает 0, 1 или 2.

`write_head` — физический индекс последней записанной ячейки (`last_index`). При пустом уровне равен 0.

`catalog_crc32` считает `crc32()` из `device_lib/src/service.c` по массиву `g_event_log_catalog[]`:

```
crc = 0x8005
crc = crc xor 0xFFFFFFFF
для каждого байта каталога:
    crc = table[(crc xor byte) & 0xFF] xor (crc >> 8)
результат = crc xor 0xFFFFFFFF
```

Таблица — reflected CRC-32 (та же, что в `service.c`). Начальное значение функции — `POLYNOM` (`0x8005`), не 0.

Элемент каталога в этой сборке (enum компилятора — 4 байта, флага `-fshort-enums` нет), 12 байт, padding нулевой:

| Смещение | Поле |
|----------|------|
| 0 | `code` u16 |
| 2 | pad u16 = 0 |
| 4 | `level` u32: 0 critical, 1 general |
| 8 | `debug_only` u8 |
| 9 | pad 3 байта = 0 |

В каталоге 27 элементов, коды 1…27 в порядке `event_log_catalog.c`, 324 байта. Для этого массива `catalog_crc32 = 0x15DF210C`.

## 6. `START_DUMP` (`0x10`)

Запрос, минимум 6 байт:

| Смещение | Поле |
|----------|------|
| 0 | `opcode` = `0x10` |
| 1 | `tier`: `0` критический, `1` общий, `2` оба |
| 2..5 | `start_logical` u32, 0 — с самой старой записи выбранного диапазона |

Короче 6 байт: ответ 2 байта, `status = 2`.

`tier > 2`: `status = 2`. Сессия уже активна: `status = 4`. Журнал не инициализирован: `status = 1`. Сбой чтения уровня: `status = 6`. Эти ошибки — ответ из 2 байт.

`start_logical`, равный числу записей диапазона, допустим: успех и `total_records = 0`. Значение больше этого числа: `status = 3`.

Успех — всегда 16 байт, в том числе при `total_records = 0`:

| Смещение | Поле |
|----------|------|
| 0 | `status` = 0 |
| 1 | `opcode` = `0x10` |
| 2..3 | `stream_id` u16, с 1, 0 пропускается |
| 4..7 | `total_records` u32 |
| 8..11 | `write_head_crit` u32, снимок на этот запрос |
| 12..15 | `write_head_gen` u32, снимок на этот запрос |

При `total_records = 0` сессия сразу гасится, кадров `LOG_DATA` нет.

Иначе конец диапазона фиксируется как `count` на момент запроса. Записи, появившиеся после старта, в этот поток не входят. `write_head` в кадрах данных — тот же снимок, он по ходу выгрузки не меняется.

### Индекс при `tier = 2`

В запросе `start_logical` сквозной: сначала критический уровень (`0 .. critical_count−1`), затем общий.

- `start_logical < critical_count` — старт внутри критического, дальше весь общий уровень.
- иначе старт внутри общего с индекса `start_logical − critical_count`.

В элементе потока `logical_index` — индекс **внутри текущего уровня**. На общем уровне он снова начинается с 0.

### Как идут кадры данных

На обработчике запроса в очередь ставится не больше 16 кадров `LOG_DATA`. Дальше `LogTransport_Process` вызывается из цикла 10 мс в `Core/Src/app.cpp` и за один вызов добавляет не больше 4 кадров. Этот вызов выполняется, когда нет задержки обработки предупреждений и `PPKYConfig.rs485_on != 0`. При выключенном RS485 после первых 16 кадров данных сессия остаётся активной, новые кадры не формируются.

Подтверждения кадра данных нет. Остановить поток можно командой `STOP_DUMP`.

## 7. `LOG_DATA`

`pkt_type = 18`, `seq = 0`.

### 7.1. Заголовок payload, 16 байт

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 2 | `stream_id` |
| 2 | 2 | `pkt_num`, с 0 |
| 4 | 1 | `flags` |
| 5 | 1 | `tier` записей этого кадра: 0 или 1 |
| 6 | 1 | `rec_count` |
| 7 | 1 | резерв, 0 |
| 8 | 4 | `first_logical` — `logical_index` первой записи кадра |
| 12 | 4 | `write_head` снимка уровня этого кадра |

**`flags`:**

| Маска | Имя | Смысл |
|-------|-----|-------|
| `0x01` | `FIRST` | первый кадр сессии |
| `0x02` | `LAST` | последний кадр, сессия после него закрыта |
| `0x04` | `TIER_CHANGE` | этот кадр заканчивает критический уровень, следующий будет общим |
| `0x80` | `ERROR` | чтение Flash оборвалось; ставится вместе с `LAST` |

`TIER_CHANGE` стоит на последнем кадре критического уровня, и только если в запросе `tier = 2` и `general_count > 0`. Байт `tier` этого кадра всё ещё 0. Если общий уровень пуст, вместо `TIER_CHANGE` ставится `LAST`.

`ERROR|LAST` ставится, если в кадре уже упакована хотя бы одна запись, а следующая не прочиталась. Если ошибка на первой записи кадра, `rec_count = 0`: кадр не отправляется, сессия закрывается.

`FIRST` и `LAST` могут стоять на одном кадре.

### 7.2. Элемент потока, 38 байт

`LOG_STREAM_REC_SIZE = 38`. Шаг разбора — 38, не 37.

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 4 | `logical_index` u32, индекс внутри уровня |
| 4 | 1 | `rec_status`: `0` сумма верна, `1` слот целиком `0xFF`, `2` сумма не сошлась |
| 5 | 1 | `tier` этой записи |
| 6 | 32 | `EventLogRecord_t` как во Flash |

Сырые 32 байта копируются и при `rec_status` 1 и 2.

В один кадр входит не больше 6 записей: `16 + 6×38 = 244 ≤ 246`. Кадр из 6 записей имеет длину 254 байта. Байтов после последней записи нет.

### 7.3. Проверка на ПО

1. `pkt_num` следующего кадра на 1 больше предыдущего.
2. `logical_index` записей кадра идут подряд от `first_logical`.
3. При `tier = 2` после кадра с `TIER_CHANGE` следующий кадр имеет `tier = 1`, а `logical_index` начинается с 0.
4. Сумма `rec_count` по всем кадрам равна `total_records` из ответа `START_DUMP`, если не было `ERROR` и обрыва связи.

Повтор после обрыва: `STOP_DUMP`, затем новый `START_DUMP`.

- Для `tier` 0 или 1: `start_logical` = последний принятый `logical_index` этого уровня + 1.
- Для `tier = 2`: пока идёт критический уровень, тот же индекс. После перехода на общий уровень сквозной индекс равен `critical_count + logical_index_общего`.

`critical_count` брать из `GET_INFO` до старта или учитывать, что снимок конца зафиксирован ответом `START_DUMP` (`total_records` и правило склейки из §6).

## 8. `STOP_DUMP` и `GET_DUMP_STATUS`

**`STOP_DUMP` (`0x11`).** Параметров нет. Ответ всегда 2 байта: `status = 0`, `opcode = 0x11`. Сессия сбрасывается, даже если её не было. Уже стоящие в очереди USART2 кадры эта команда из очереди не вынимает.

**`GET_DUMP_STATUS` (`0x12`).** Ответ всегда 11 байт, `status = 0`:

| Смещение | Размер | Поле |
|----------|--------|------|
| 0 | 1 | `status` |
| 1 | 1 | `opcode` = `0x12` |
| 2 | 1 | `active`: 1 — сессия идёт |
| 3 | 2 | `stream_id` |
| 5 | 2 | `pkt_sent` — сколько кадров `LOG_DATA` поставлено в очередь |
| 7 | 4 | `records_sent` — сколько элементов потока упаковано |

## 9. Логический индекс

```
capacity = tier.capacity
count    = tier.count          /* total_records, не число валидных CRC */
head     = tier.write_head     /* last_index */

oldest   = (count == 0 || count < capacity) ? 0 : ((head + 1) % capacity)
physical = (oldest + logical_index) % capacity
```

`logical_index = 0` — самая старая запись уровня, `count − 1` — самая новая. Индекс `≥ count` чтение не возвращает.

Классификация слота при чтении (`Core/Src/event_log_reader.c`): все байты `0xFF` → `empty`; иначе CRC-16 не сошлась → `invalid`; иначе `valid`.

## 10. Сценарий ПО

```
1. LOG_REQ PING
2. LOG_REQ GET_INFO
3. LOG_REQ START_DUMP(tier, start_logical)
4. LOG_RSP: stream_id, total_records, два write_head
5. Приём LOG_DATA, пока нет LAST:
     pkt_num, flags, rec_count
     rec_count элементов по 38 байт
     rec_status = 0 → разбор 32 байт по event_log_catalog.json
6. При обрыве: STOP_DUMP и START_DUMP с индексом из §7.3
```

Кадры типов 0 и 1 на том же USART2 пропускать: это CAN-мост.
