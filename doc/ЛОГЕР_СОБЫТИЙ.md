# Описание работы логера событий

## Архитектура (два уровня)

Логер разделён на **два независимых циклических буфера** во внешней SPI Flash (после области конфигурации ППКУ). Размеры уровней **разные**:

| Уровень | Секторы Flash (W25Q128, сектор 4096 байт) | Записей (до перезаписи) |
|---------|------------------------------------------|-------------------------|
| **Критический** | 288 … 687 (400 секторов) | **51 200** (400 × 128) |
| **Общий** | 688 … 4095 (3408 секторов) | **436 224** (3408 × 128) |

Журнал начинается с сектора `FLASH_LOG_START_SECTOR` = 288 (`0x00120000`). До него: конфигурация (секторы 0…31), слот factory `0x00020000` и слот update `0x000A0000` размером 512 КБ (`Core/Inc/boot_layout.h`, `Core/Inc/app.hpp`).

Критический уровень: не меньше 50 000 записей (`FLASH_LOG_CRITICAL_MIN_RECORDS`), фактически 400 секторов. Общий уровень занимает остаток до конца микросхемы (4096 секторов). Незанятого хвоста нет (`FLASH_LOG_UNUSED_TAIL_SECTORS` = 0). В секторе 128 записей по 32 байта.

До первого заполнения буфера записи идут без потерь. После заполнения включается кольцевая перезапись: при переходе на новый сектор стирается весь сектор целиком — теряется **128** записей (минимальная единица erase Flash).

Константы и проверка на этапе сборки: `app.hpp`, `event_log.cpp` (`static_assert`).

### Файлы реализации

| Файл | Роль |
|------|------|
| `Core/Inc/event_log_catalog.h`, `event_log_catalog.c` | Коды событий, уровень (critical/general), флаг `debug_only` |
| `Core/Inc/event_log.h`, `event_log.cpp` | API: `EventLog_Init`, `EventLog_Post`, `EventLog_SetDebug` |
| `Core/Inc/event_logger.h`, `event_logger.cpp` | Низкоуровневый кольцевой буфер одного уровня |
| `Core/Inc/app.hpp` | Разметка SPI Flash (конфиг + лог) |

### API (без привязки к местам вызова)

```c
EventLog_Init(&hFlash);                    // после SPIF_Init
EventLog_SetDebug(1);                      // разрешить debug-only события в GENERAL
EventLog_Post(EVENT_LOG_FIRE_DETECTED, &payload);

const EventLogCapacityInfo_t *cap = EventLog_GetCapacityInfo();
// cap->critical_record_capacity, cap->general_record_capacity, cap->records_lost_on_sector_wrap
```

`EventLogPayload_t` — поля записи кроме времени и CRC (заполняются автоматически).

### Каталог событий и debug-режим

Маршрутизация задаётся в `g_event_log_catalog[]` (`event_log_catalog.c`):

- `level = CRITICAL` → критический буфер
- `level = GENERAL` → общий буфер
- `debug_only = 1` → пишется в **общий** буфер только при `EventLog_SetDebug(1)` (диагностика, телеметрия)

Для добавления события: новый код в `EventLogCode_t` + строка в каталоге.

**Машиночитаемая спецификация для внешнего ПО** (парсинг, формирование записей, CRC): [`event_log_catalog.json`](event_log_catalog.json) — формат записи 32 байта, CRC, CAN ID, поля `additional`/`can_data` по каждому коду события.

## Общие сведения

Логер событий пишет значимые события во внешнюю SPI Flash. Запись фиксирована: **32 байта**. В секторе 4096 байт таких записей 128.

## Формат записи лога

Каждая запись лога имеет следующую структуру:

| Смещение | Размер (байт) | Назначение | Описание |
|----------|---------------|------------|----------|
| 0        | 6             | Время события | BCD: год, месяц, день, час, минута, секунда |
| 6        | 1             | Номер мастера/вагона | Номер мастера (шины) или номер вагона в составе |
| 7        | 1             | Резерв | Зарезервировано для будущего использования |
| 8        | 2             | Код события | Уникальный идентификатор типа события|
| 10       | 4             | CAN заголовок | CAN заголовок (формат описан в `device_lib backend.h`) |
| 14       | 8             | Данные CAN сообщения | Данные из CAN сообщения (до 8 байт) |
| 22       | 8             | Дополнительная информация | Дополнительная информация, специфичная для события |
| 30       | 2             | Контрольная сумма | CRC-16 по байтам [0..29]: старт `0xFFFF`, полином `0x1021` |

**Итого: 32 байта**

## Коды событий

Нумерация ниже — действующий каталог `Core/Inc/event_log_catalog.h` и `Core/Src/event_log_catalog.c`. Поля `additional` / `can_data` / `can_header` по каждому коду — в [`event_log_catalog.json`](event_log_catalog.json). Здесь только то, что писатель в прошивке реально кладёт в запись.

`master_wagon_num` у всех писателей — `PPKYConfig.UId.devId.h_adr`. Байт 7 (резерв) при записи 0. Время — BCD из RTC: год, месяц, день, час, минута, секунда. Исключение — код 2, см. ниже.

`can_header` — `can_ext_id_t` из `device_lib/include/backend.h`, маска `0x1FFFFFFF`, little-endian: биты 0…6 зона, 7…12 `l_adr`, 13…20 `h_adr`, 21…27 `d_type`, 28 `dir`. Писатели, которые собирают заголовок сами, ставят `dir = 1`.

### 1. `EVENT_LOG_MASTER_START` — критический

Пишет `EventLog_LogMasterBoot`. `can_header` = 0, `can_data` = 0, `additional[0]` = 0. Время — текущее RTC.

### 2. `EVENT_LOG_MASTER_STOP` — критический

Та же функция, и только если в `RTC_BKP_DR1` есть метка прошлого включения и её месяц/день/час/минута — допустимый BCD. `additional[0]` = 1. Секунды в записи — 0. Год берётся из текущих часов; если месяц-день-час-минута метки позже текущего момента, год уменьшается на 1 (с переходом 00 → 99). Если метки нет, запись не создаётся.

### 3. `EVENT_LOG_SYSTEM_START_OK` — критический

Код есть в каталоге. Вызова `EventLog_Post` с этим кодом в прошивке нет.

### 4. `EVENT_LOG_DEVICE_MISSING` — общий

`config_monitor.cpp`. `can_header` — устройство из конфига. `can_data` = 0. `additional[0]`: 0 появилось, 1 снято. `additional[1]` — слот `CfgDevices`. `additional[2]` — `l_adr` канала, 0 если отсутствует МКУ целиком.

### 5. `EVENT_LOG_DEVICE_FOUND` — общий

`can_header` — фактический ID. `can_data` = 0. `additional[0]`: 0 появилось, 1 снято.

### 6. `EVENT_LOG_CONFIG_MISMATCH` — общий

Периодическая проверка CRC, период `CM_CRC_PERIOD_MS` = 5000 мс. `can_header` — МКУ. `can_data` = 0. `additional[0]`: 0 расхождение, 1 снято. `additional[1]` — слот. `additional[2]` = 0.

### 7. `EVENT_LOG_TELEMETRY` — общий, `debug_only`

`EventLog_LogCanTelemetry` кладёт `can_header` (маска `0x1FFFFFFF`), 8 байт `can_data` и `additional[0]` = 0. Функция ниоткуда не вызывается. `EventLog_SetDebug` тоже ниоткуда не вызывается, флаг debug при старте 0. В обычной работе запись не создаётся.

### 8. `EVENT_LOG_DEVICE_FAULT` — критический

`warning.cpp`. `additional[0]` — класс: 0 обрыв, 1 КЗ, 2 ошибка протокола линии, 3 CAN, 4 питание, 5 прочее, 6 позиция МКУ. `additional[2]`: 0 появилась, 1 снята. Неисправность журнала панели (`WARN_KIND_PANEL_JOURNAL_FAULT`) в лог не пишется.

- Виртуальный канал: `can_header` устройства, `can_data[0]` = `status_cmd`, `can_data[1..7]` = `status_params`, `additional[1]` = `l_adr`.
- CAN МКУ или ППКУ: `can_data[0]` = состояние линии, `can_data[1]` = индекс CAN, `additional[1]` = индекс CAN. Для ППКУ в заголовке тип ППКУ и его `h_adr`.
- Позиция МКУ: заголовок ППКУ, `can_data[0]` и `additional[1]` = `h_adr` МКУ.
- Питание: заголовок ППКУ, `can_data[0]` = 0 выход питания / 1 вход ППКУ, `can_data[1]` и `additional[1]` = канал 1 или 2, класс = 4.

### 9. `EVENT_LOG_FIRE_DETECTED` — критический

`fire.c`. `can_header` — ID сообщения, маска `0x1FFFFFFF`. `can_data` — 8 байт этого сообщения, если указатель не пустой. `additional[0]` — зона (биты 0…6). `additional[1]` — источник, который возвращает `Fire_LogDetectSource`: 0 ДПТ, 2 кнопка, 3 прочее внешнее. Константы 1 (термопара) и 4 (ручной) в этом вызове не возвращаются.

### 10. `EVENT_LOG_EXTINGUISH_START` — критический

`additional[0]` — тип пуска: 0 ручной, 1 автоматический (`fire_mode` = 0), 2 автономный (`fire_mode` = 1). `additional[1]` — зона. `additional[2]` — задержка зоны в секундах (`Fire_ZoneDelaySec`).

### 11. `EVENT_LOG_EXTINGUISH_FORCE_STOP` — критический

Пишется, только если есть активный слот пожара и причина не `0xFF` (`FIRE_LOG_STOP_NO_EVENT`). `additional[0]`: 0 оператор, 1 концевик, 2 неисправность, 3 смена режима, 4 прочее. `additional[1]` — зона аргумента вызова. `additional[2]` — `PPKYConfig.fire_mode`.

### 12. `EVENT_LOG_EXTINGUISH_COMPLETE` — критический

Один раз на цикл (`log_complete_posted`). `additional[0]` = 0 (`FIRE_LOG_COMPLETE_FULL`). `additional[3]` = 0. Байты 1 и 2 остаются 0. Маска пропущенных шагов не записывается.

### 13. `EVENT_LOG_EXTINGUISH_INCOMPLETE` — критический

Один раз на слот. `additional[0]`: 0 нет ответа, 1 неисправность спички, 2 таймер, 3 оператор, 4 конфиг, 5 прочее. `additional[1]` — `g_fire.state`. `additional[2]` — зона слота. `additional[3]` не заполняется.

### 14. `EVENT_LOG_PANEL_BUTTON` — критический

Принятое действие, не сырое касание (сырое — код 23). `additional[0]`: 0 ПУСК ОБЩИЙ, 1 ПУСК СП, 2 ОСТАНОВ. `additional[1]` — зона, 0 если глобально. `additional[2]` — `fire_mode`. `additional[3]` — секунды удержания, которые передал вызов (в местах пуска общего встречается 3, у сброса пожара по удержанию ОСТАНОВ — 5, у части нажатий — 0).

### 15. `EVENT_LOG_HOST_LINK` — критический

Один раз на канал, пока сессия не сброшена. `additional[0]`: 0 USART2 / Wi‑Fi, 1 был бы UART4. Сейчас в этот писатель попадает только 0: запрос журнала на USART2 и команда конфига с `BUS_UART1`. Сброс канала 0 — `Esp32_SetEnabled(0)`. `additional[1]` писатель не заполняет.

### 16. `EVENT_LOG_CONFIG_APPLY_OK` — критический

После успешного APPLY всех целевых МКУ. `additional[0]` — сколько МКУ залито, `additional[1]` — сколько было в цели. Следом `EventLog_LogAllCfgMcusSaved` пишет код 22 по каждому слоту типа МКУ.

### 17. `EVENT_LOG_CONFIG_APPLY_FAIL` — критический

Только операции APPLY и подфаза APPLY синхронизации блока спичек. `can_header` — ID МКУ, `dir` = 1. `additional[0]`: 0 таймаут, 1 неверный размер, 2 несовпадение эха, 3 несовпадение CRC. `additional[1]` — слот, `[2]` — `h_adr`, `[3]` — зона, `[4]` — `d_type`.

### 18. `EVENT_LOG_SOUND_TOGGLE` — критический

`additional[0]`: 0 выкл, 1 вкл. `additional[1]`: 0 панель RS (`rs_panel_v3_master.c`, если значение `beep` изменилось), 1 автоматическое включение звука на новом событии (`Beeper_ResumeSoundOnNewEvent`, только `GOST_MODE`).

### 19. `EVENT_LOG_FIRE_MODE_CHANGE` — критический

`EventLog_LogFireModeChange` записывает `additional[0]` = режим, `additional[1]` = источник. Вызовов этой функции в прошивке нет.

### 20. `EVENT_LOG_TELEMETRY_SAMPLE` — общий

Раз в `EVENT_LOG_TELEMETRY_SAMPLE_PERIOD_MS` (10 минут), не больше `EVENT_LOG_TELEMETRY_SAMPLE_BUDGET` (4) записей за вызов 10 мс цикла. `can_header` устройства, `dir` = 1. `additional[0]`: 0 статус МКУ (`mcu_status_data`, 8 байт), 1 виртуальный канал (`can_data[0]` = `status_cmd`, далее 7 байт `status_params`). Debug не требуется.

### 21. `EVENT_LOG_FIRE_RESET` — критический

`additional[0]` — зона. `additional[1]` — источник; единственный вызов передаёт 0 (удержание ОСТАНОВ на панели). `additional[2]` — `fire_mode`.

### 22. `EVENT_LOG_MCU_SAVED` — критический

Только типы МКУ: 13, 14, 20, 21, 22, 23. `can_header` — ID устройства, `dir` = 1. `can_data` — `UId0` и `UId1`, little-endian по 4 байта. `additional[0..3]` — `UId2`, little-endian. `UId3` и `UId4` в запись не входят.

### 23. `EVENT_LOG_PANEL_BTN_PRESS` — критический

Сырое касание, без проверки автомата пожара. `additional[0]` — та же нумерация кнопок, что у кода 14. `additional[1]` — зона. `additional[2]` — `fire_mode`. Байта удержания нет.

### 24 и 25. `EVENT_LOG_COUNTDOWN_PAUSE` / `EVENT_LOG_COUNTDOWN_RESUME` — критические

`additional[0]` — зона (0, если вызов глобальный). `additional[1]`: 0 панель, 1 CAN. `additional[2]` — `fire_mode`.

### 26. `EVENT_LOG_CONFIG_SAVED` — критический

`SaveConfig` ППКУ. `additional[0]` — сколько зон с непустым именем, `additional[1]` — `ZONE_NUMBER` (100). Если эта запись не легла во Flash, имена зон следом не пишутся.

### 27. `EVENT_LOG_ZONE_NAME` — критический

Сразу после кода 26, по одной записи на зону, у которой первый символ имени не 0. Номер зоны 1…100 лежит в поле `zone` заголовка; `d_type` = 10 (ППКУ), `h_adr` ППКУ, `dir` = 1. Имя — до 16 байт: `can_data[0..7]`, затем `additional[0..7]`. Имя в конфиге длиннее 16 байт обрезается. Короткое имя дополняется нулями. Номер зоны в `additional` отдельно не дублируется.

## Примеры

Запись кода 1, little-endian:

```
[0..5]  BCD: год, месяц, день, час, минута, секунда
[6]     h_adr ППКУ
[7]     0
[8..9]  код 1
[10..13] 0
[14..21] 0
[22]    0
[23..29] 0
[30..31] CRC-16 по байтам [0..29]
```

Запись кода 4:

```
[10..13] can_ext_id устройства из конфига, dir = 1
[14..21] 0
[22]    0 появилось / 1 снято
[23]    слот CfgDevices
[24]    l_adr канала или 0 для МКУ целиком
```

## Примечания по реализации

1. Запись 32 байта. Единица стирания — сектор 4096 байт, в нём 128 записей.
2. Время — BCD RTC STM32, порядок байт: год, месяц, день, час, минута, секунда.
3. Раскладка `can_header` — `can_ext_id_t` в `device_lib/include/backend.h`.
4. Контрольная сумма — CRC-16 по байтам [0..29]: старт `0xFFFF`, полином `0x1021`, без отражения битов и без xor на выходе (`EventLogTier_CalculateChecksum`).
5. Два кольцевых буфера. При переходе на новый сектор стирается весь сектор, пропадают 128 записей.
6. Отдельного флага «запись дописана» нет: пустой слот — 32 байта `0xFF`, целость — CRC-16.
